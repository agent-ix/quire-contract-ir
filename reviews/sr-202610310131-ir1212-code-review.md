## Evidence

The tuple-row loop charges once per row and then clones `row.node_key` into `exact_keys`; the projection clones the key again into its output. The source-unit path similarly clones `UnitId` and the qualified declaration. `NodeKey` and `UnitId::Declared` are caller-provided opaque stage claims, and the row constructors impose no payload length bound. A valid `Pair` tuple row whose key contains a multi-megabyte `PathSegment::Text` succeeds under the same limit and reports the same `work()` as a short key. Charge the full key and row payload before cloning, using checked arithmetic and the same refusal locus.

## New findings (disposition pass 1)

| ID | Severity | Summary | Refs |
| --- | --- | --- | --- |
| FND-002 | medium | The new admitted-row overlay clones the entire FR-352 identity table, including deep field-row strings, before charging their size against the projection limit. | crates/quire-contract-model/src/checked_package/v2/exact_projection.rs:460 |

The first fix charged tuple and source-unit row payloads but left `SelectedExactIdentities::with_admitted_type_rows` calling `self.clone()`. Locked `quire-exact` uses an `Arc` shallow clone for `NodeKey`, so the key-copy memory example in the original evidence overstated that cost. `SelectedExactFieldRow` owns `Box<str>` selected document and original identities plus a `MemberId.member: String`; cloning many long, otherwise valid selected field rows remains proportional to their total string length while the new projection charged only constant work per row. The helper is newly introduced by this PR.
